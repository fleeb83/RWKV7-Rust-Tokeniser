# Version 0.2.0 benchmark summary

Measured on Windows with an Intel Core i9-14900HX (32 logical CPUs),
2026-09-08. This release promotes the frozen candidate used in these checks.
The original package was backed up before promotion.

## Throughput

A fresh 70-case holdout used six publicly available
[Canterbury corpus](https://corpus.canterbury.ac.nz/descriptions/) files,
with whole documents, 8 KiB chunks and short lines. It was frozen before the
last optimization experiments and excluded exact prior training/holdout texts.
It represents English text and code, not multilingual performance coverage.

Each comparison used seven rotating trials of at least 0.5 seconds with both
implementations in one executable at BelowNormal priority. Cahya was pinned to
commit `63b21e891d0c8efd95997d797049bb7f92098d8c`.
Ratios are geometric means of group median throughput; above one favors this
release. They do not predict every application's performance.

| Operation | Speed versus Cahya |
|---|---:|
| Single encoding, aggregate | 1.302x |
| Whole-document encoding | 1.619x |
| 8 KiB chunk encoding | 1.652x |
| Short-line encoding | 0.826x |
| Batch encoding, aggregate | 2.163x |
| UTF-8 decoding, aggregate | 3.762x |
| Vocabulary construction | 0.921x |

Batches of 1, 2, 6 and 32 used Cahya's actual `encode_batch` in a local
one-worker Rayon pool, matching the candidate's active-worker budget on this
host. These results do not compare against unrestricted 32-worker Rayon.
Loading took 174.86 ms versus 161.10 ms. In the separate training screen,
encoding averaged 1.067x; its 1 MiB group remained slower at 0.921x.
Tiny 1–32 byte training strings took about 151 ns versus 78 ns, reflecting
fixed cooperation overhead.

## Correctness and responsiveness

The frozen sources passed 23 release unit tests, 94 training reference cases,
70 holdout cases with complete batch outputs, 11,718 custom-vocabulary cases,
and 256 raw-byte cases. Reference token IDs were pinned to official BlinkDL
implementations. Identity, arithmetic and artifact-hash audits passed, including
intentional corrupted-output and broken-counter rejection checks.

Two separately constructed tokenizers shared one active-worker gate in two
foreground probes. Both processes ran at Normal priority; only the foreground
probe was pinned to logical CPU 0, while tokenizer load retained all 32 CPUs.
Each 10-second loaded phase was bracketed by 10-second idle phases.

| Run | Median service, idle to loaded | p95 service, idle to loaded | Average CPU cores used by load |
|---|---:|---:|---:|
| A | 207.5 to 207.7 us | 252.4 to 237.2 us | 0.253 |
| B | 219.5 to 228.3 us | 269.3 to 274.3 us | 0.368 |

The probes completed 11,001 and 10,531 calls. Both passed predefined limits of
+10% median service, +20% p95 service and +2 ms wake-lateness p95. This supports
bounded observed impact for this synthetic foreground workload on this host.
It is not a zero-interference guarantee or certification of every machine.

The gate adapts to reported CPU availability and tokenizer contention, not
external OS load. Construction and full UTF-8 validation acquire the gate but
are not internally interruptible. No thread priority or affinity is changed
by the library. Runtime dependencies remain empty; no unsafe Rust was added.
